# 10 常见故障排查手册

## 1. 排查原则

按“**格式 → API 状态 → Buffer 所有权 → Work 队列 → FDK → PCM/PTS → 部署版本**”顺序定位。每次只改一个变量，保存输入副本、源码 HEAD、设备 fingerprint、组件名和完整日志。

不要：

- 把所有 `.aac` 当 ADTS，或把 M4A 改扩展名当裸流。
- 用 PTS 减 `System.nanoTime()`。
- 假定 Work 输入与 PCM 输出一一对应。
- 只看 `lshal`/XML 就断言实际组件。
- 在生产设备插入 sleep 或随意替换 APEX/系统库。

## 2. 快速诊断表

| 现象 | 优先检查 | 证据/下一步 |
|---|---|---|
| 找不到 AAC track | 容器与 MIME | `ffprobe`；Extractor track format；是否真 AAC |
| `createByCodecName` 失败 | 设备组件名 | 运行 `enumerate`；不要硬编码后跳过枚举 |
| configure 失败 | CSD/profile/rate/channels | 打印 format、CSD 长度；ConfigRaw 返回 |
| start 非法状态 | configure/start/stop/release 顺序 | Java 堆栈与 Native kWhat 消息 |
| 只有输入无输出 | EOS、输出循环、延迟、反压 | outputWait、pending、Buffer release |
| `INFO_TRY_AGAIN_LATER` 持续 | 输入是否耗尽/输出持有 | 持有 Buffer 实验；Work queue |
| 输出 PCM 爆音 | s16le/交错/rate/channels | `format_changed`；ffplay 参数 |
| PCM 时长不对 | priming/padding/edit list | 样本计数、容器元数据、outputDelay |
| PTS 不连续 | 源容器/Flush/输出补偿 | ordinal、frameIndex、configUpdate |
| Flush 后旧帧 | generation/pending/ring | `C2_NOT_FOUND`、onFlush_sm |
| EOS 缺尾 | drain/AACDEC_FLUSH | 最后 pending work、EOS flags |
| 错误后静音 | 本层错误替换 | DecodeFrame result、CLEAR_BUFFER |
| 编码 result OK 但无有效流 | FDK 错误未传播 | C2SoftAacEnc encoderErr 日志 |
| Native 日志完全不存在 | 属性/进程/库部署 | setprop、进程重启、实际加载库/APEX |
| 源码与设备行为不同 | 构建版本不一致 | HEAD、本地 diff、fingerprint、库 hash |

## 3. 格式与 CSD

### M4A 被当 ADTS

**症状：** syncword 错误、随机 frame length、configure 后数据异常。

**处理：** M4A 走 MediaExtractor，format 携带 CSD，sample 是 RAW AAC access unit；不要用 ADTS parser 读 container bytes。

### ADTS `channel_configuration=0`

**症状：** 实验 App 明确报 PCE 不支持。

**处理：** 换常规 channel configuration 样例，或扩展 PCE 解析；不能按 0 声道或默认双声道猜。

### 错误 ASC/CSD

**源码位置：** `C2SoftAacDec.cpp:649-668`。ConfigRaw 失败置 `mSignalledError/C2_CORRUPTED`，成功不产 PCM。

**处理：** 打印 ASC 字节，核对 object type、sample index、channel config。不要通过重试相同 CSD 期待恢复。

## 4. API 状态与 Buffer

### configure 前 start

公共 API 应抛状态异常。`CodecFaultTest` 已包含实验。记录实际异常，不用 catch 后继续当正常状态。

### 输出 Buffer 不释放

**机制：** 可用缓冲逐渐减少，输入/输出均可能反压。持有 4 个只是实验条件，不是池大小。

**处理：** 对每个 `index>=0` 使用 try/finally `releaseOutputBuffer`；包括 size=0、EOS 和异常路径。核对 `outputCount==outputReleasedCount`。

### EOS 后无退出

确认输入 EOS 只提交一次、仍继续 dequeue 输出直到输出 EOS。不要在输入 EOS 后立即 stop，否则可能丢尾。

### 120 秒 stall

本实验是保护性超时，不是 Android 合同。保存前后最后 input/output/format 事件，检查是否有 output index 未释放、组件 pending、Binder death 或 Native 死锁。

## 5. CCodec / Work / 线程

### Work 入队后无完成

1. `queue_nb` 是否 RUNNING、返回何值。
2. WorkHandler 是否收到 kWhatProcess。
3. `process()` 是否返回但 `workletsProcessed=0` 入 pending。
4. 输出 pool 是否可用。
5. EOS/drain 是否最终完成 pending。
6. Listener→CCodec workDoneQueue→handleWork 是否中断。

### Flush 竞态

本树 `flush_sm` 与 `onFlush_sm` 分两阶段。处理中的旧 Work 由 generation 检查，可能 `C2_NOT_FOUND`。若旧帧仍出现，查回调是否已在上层队列、App 是否保留旧 Buffer。

### 耗时异常

分别统计：

- queueDelay：排队是否过长。
- decodeCost：FDK/组件实际处理。
- callbackLag：完成回调排队。
- App outputWait：包含以上及 App 调度，不可替代前三项。
- 播放端到端：还含 AudioTrack/AudioFlinger/HAL，不在 decodeCost 内。

负耗时首先检查时钟域和事件配对，不要取绝对值掩盖。

## 6. FDK-AAC 数据问题

### NOT_ENOUGH_BITS

本层等待更多输入，通常可恢复。若一直到 EOS 仍不足，可能最后一帧截断；检查 drain 错误和尾部输出。

### 其他 DecodeFrame 错误

本树 `C2SoftAacDec` 记录警告、替换一帧静音、丢弃剩余输入并清 transport。出现静音不一定代表 FDK 原始 concealment 就是静音。

### Fill 返回值

本层 `aacDecoder_Fill` 返回值被忽略。实验补丁可记录但不改变默认行为。重点看 `bytesValid`、offset/size 是否推进；不推进会导致异常或死循环风险。

### 动态采样率/声道

通过 `configUpdate` 和 App `INFO_OUTPUT_FORMAT_CHANGED` 观察。无头 PCM 不能安全混放两种格式，应分段输出或封装 WAV。

## 7. 编码与 Mux

### Muxer 未 start

等 `INFO_OUTPUT_FORMAT_CHANGED` 后 addTrack/start，再写 compressed sample。CSD Buffer 不当普通 sample 写。

### 尾部丢失

检查 EOS 输入、`numInSamples=-1`、最后 output EOS、Muxer stop/release。不要在编码输出 drain 前 stop。

### Priming 对齐

先用容器元数据，再用 `compare_pcm.py --scan-delay` 辅助。固定裁 1024 不是通用解法；AAC 有损，比较有效区间的 RMS/SNR 和样本数。

## 8. 构建、部署与设备证明

### APK 构建

- JDK/Gradle：Wrapper 为 8.9，AGP 8.7.3，推荐 JDK 17。
- SDK：compileSdk 35；设置 `ANDROID_HOME` 或 `local.properties`，不要把源码树的单独 `android.jar` 当完整 SDK。
- 本次只完成 API 35 javac 检查，不代表 APK 已构建。

### Native 库部署

软件 AAC 可能位于 `com.android.media.swcodec` APEX。需确认实际装载路径、APEX 签名、AVB/动态分区和进程重启。`push` 一个未被加载的同名库不等于部署成功。

### 证明进入软件 AAC

同时保存：

1. `MediaCodecList` 枚举和显式组件名。
2. `C2SoftAacDec::process` 的可验证日志/断点。
3. `aacDecoder_Fill/DecodeFrame` 结果与输出格式。
4. PCM/JSONL 和 EOS/释放计数。

缺少任一项时写“尚未证明”，不要写“已走软解”。

## 9. 推荐日志采集模板

```sh
adb shell getprop ro.build.fingerprint
adb shell setprop debug.audio.codec.trace 1
adb shell setprop debug.audio.codec.delay.ms 0
adb logcat -c
# 运行一次 decode_m4a
adb logcat -d -v threadtime -s AudioCodecDebugger C2SoftAacDec SimpleC2Component > aac_trace.log
adb shell setprop debug.audio.codec.trace 0
```

属性是否需要重启进程取决于补丁读取时机；当前补丁按 Work 读取，仍建议每个用例重启实验进程以隔离状态。日志数值只有在真实采集后才可标为“实测”。

## 10. 上报问题最小信息

- 源码根、子仓库 HEAD、本地 diff。
- 设备 fingerprint、Android/SDK、ABI。
- 输入格式、CSD/ADTS 信息、样本时长。
- 实际 Codec 名称及软件/厂商属性。
- App JSONL、Native threadtime log、异常堆栈。
- PCM 参数、输入/输出/EOS/释放计数。
- 复现步骤、是否必现、最后一次正常操作。
- 是否应用补丁、属性值、部署库路径/hash。
